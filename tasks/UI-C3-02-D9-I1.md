## Audit remediation I15 (against `423b9f9`; D9 still pending, live default-off)

- MAJOR-1: exclusive cross-process record ownership. Atomic hard-link lock
  acquisition (`O_EXCL` semantics); contention or a live foreign holder
  refuses `LIVE_RECORD_LOCKED`; a stale lock is taken over only when its tip
  is still in the record chain; every send re-verifies lock ownership at the
  boundary (denial poisons the live path, nothing sent). Proven by two-handle
  contention and stale-takeover tests plus a two-companion same-record test
  (second refuses, total sends 0).
- MAJOR-2: no automatic re-arm. Missing/empty records initialize only with an
  explicit owner bootstrap approval id (`--live-approval-id`,
  `liveBootstrapApprovalId`); corrupt chains always refuse (approval cannot
  launder corruption); rollback behind a surviving lock tip refuses
  `LIVE_SPEND_RECORD_ROLLBACK` and requires manual reconciliation + fresh
  approval; fsync after every append durably commits the debit before egress.
  Residual, documented: rollback that also removes/replaces the lock is
  locally indistinguishable — the runbook requires owner reconciliation on
  any unexpected budget restoration.
- MINOR-1: status reflects the real gate. New `describeActivationState`
  (unit-tested for disabled + hypothetical approved states); `/api/status`
  `config.modelOk`/`d9` and `live.*` wording derive from `validateLiveModel`;
  CLI `status` reports `mock-only` vs `live-armed`.
- MINOR-2: file hardening. Records and locks must be absolute/canonical
  regular files, not symlinks, owner-owned, with no group/other access
  (0600-style); violations refuse `LIVE_RECORD_UNSAFE`. Negative tests for
  each class.
